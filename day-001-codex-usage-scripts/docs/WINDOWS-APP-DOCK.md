# Windows 창 부착 모드 개발 기록

2026-10-27. 공개 배포·설치본 교체 전의 Windows 전용 개발 기능이다. macOS에는 추가하지 않았다.

설정 → 위치 → **Codex 창 안에 표시**를 선택하면 Pet 없이 앱 우측 하단에 대시보드를 표시한다. 기존 above/below/free/hidden 설정과 기본값은 유지한다.

## 창 부착과 디자인

- Native AppDock은 같은 로그인 세션의 실제 Codex/ChatGPT 메인 창을 선택한다. 창 제목·계정 정보는 저장하지 않는다. 최소화·cloaked·닫힘·다른 앱 전환 시 숨긴다.
- Codex 소유의 외부 도구 창이며 DOM 주입·앱 파일 패치·SetParent를 사용하지 않는다. 전역 항상 위 표시를 끈다. 위치와 공간 관찰이 정해진 뒤 표시하고 180ms 안정화 시간을 둔다. 이동·크기 조절 중에는 숨기며 조작이 끝난 후 복원한다. 창 위치를 고속으로 추적하는 방식은 사용하지 않는다.
- 기본형 308 DIP·두 열과 좁은형 224 DIP·한 열을 가용 공간에 따라 자동 선택한다. 사용자가 레이아웃을 선택하는 옵션은 없다. 여백이 더 좁으면 접힌 요약으로 시작한다. 원형 5시간/주간 사용량, 초기화권, 잔여 크레딧을 표시한다. 초기화/크레딧 알림도 내부에 배치한다. 기존 Pet 모드의 별도 알림 창은 유지한다.
- 항상 보이는 톱니바퀴 버튼으로 설정을 연다. 오른쪽 접기 버튼은 180ms 애니메이션으로 아래쪽 위치를 유지하며 접고 펼친다. 접기 상태는 저장한다.
- Codex TOML의 허용한 테마·색·폰트 필드만 읽는다. 시스템/라이트/다크·사용자 색을 따르며, 불완전한 파일 쓰기 중에는 마지막 정상 테마를 유지한다. 추종 OFF 시 기존 스타일 설정을 사용한다.
- 사이드바 폭을 고려해 우측 여백을 계산한다. 입력창 경계를 접근성에서 제공하지 않으면 패널 바깥의 3픽셀 색상 띠를 백그라운드에서 확인한다. 입력창이 넓어지면 그 위로 피하고, 두 번 연속 빈 여백이 확인되면 원래 하단 16 DIP 위치로 복원한다. 문자를 읽거나 이미지를 저장하지 않는다. 확인할 수 없을 때는 하단 200 DIP를 보호하고, 높은 입력 커서도 추가로 피한다. 우측 패널이 공간을 점유하면 접힌 요약으로 전환한다. 자동 접힘은 상태 전환 시 한 번만 적용하며 사용자의 펼치기를 매 틱 취소하지 않는다. 패널을 놓을 최소 높이·너비 자체가 없으면 숨긴다. 작은 툴팁과 일시적 관찰 가림은 마지막 정상 배치를 유지한다.
- 색상 확인은 전면 Codex 창의 알려진 영역에서만 수행한다. 사이드바 폭은 로컬 상태 파일의 숫자 필드만 백그라운드로 읽고 캐시한다. 다른 Codex 상태 값은 보관하지 않는다.

## 조회 상태와 세션 지표

일시 오류에는 최근 사용량과 마지막 확인 시각을 표시한다. 초기화 경계가 지났는데 새 응답이 없으면 이전 퍼센트를 가린다. 초기화권 상세는 동일 계정·개수·주기에 한해 유효한 최근 정보를 최대 120초 유지하고 조회 지연을 구분한다. 계정/주기 변경·만료·명시적인 빈 목록은 재사용하지 않는다.

세션 토큰/캐시/비용/속도 차트는 기본 ON이며 각각 끌 수 있다. 로컬 JSONL 수치 메타데이터를 비동기로 읽고 본문은 사용하지 않는다.

- 지정 대화 ID, 실행 시 전달받은 대화 ID, 최근 로컬 대화 순으로 선택한다. 최근 로컬 대화는 화면 선택과 다를 수 있으며 출처를 표시한다.
- 비용은 모델명과 USD/백만 토큰 단가를 지정한 경우만 계산한다. 최근 관찰한 요청의 추정값이며 전체 청구액/구독 비용이 아니다. 단가가 없으면 미설정으로 표시한다.
- 속도는 완료된 턴 출력 토큰/기록된 턴 소요 시간이다. 도구·대기가 포함되며 순수 생성 TPS가 아니다. 완료 기록이 없으면 미제공이다.
- 최신 비압축 JSONL 마지막 8MiB를 읽는다. 파일/발견 캐시가 있고 외부 전송이나 추가 계정 조회는 없다.

## 작업표시줄 위젯

별도 ON/OFF 옵션이다. 메인 모니터의 표시 데이터를 받는 WinForms 도구 창을 **숨겨진 아이콘 화살표 왼쪽** 빈 공간에 배치한다. 화살표의 실제 접근성 경계를 우선하고, 없으면 알림 영역 경계를 사용한다. 접근성 조회는 배경 스레드에서 캐시한다. 앱 버튼/알림 영역과 겹치면 더 왼쪽으로 이동하거나 숨긴다. Explorer 수정이나 공간 예약은 하지 않는다. 가로 기본 작업표시줄만 지원한다.

클릭하면 설정창을 연다. Codex 비활성·옵션 OFF·모니터 종료 시 보조 프로세스를 종료하고, 데이터가 오래되면 숨긴다. 전체 화면·작업표시줄 자동 숨김도 고려한다. 계정 요청은 추가하지 않는다.

`TaskbarDesign.cs`는 작은 원형 게이지·한도 이름·퍼센트와 초기화까지 남은 시간을 직접 그린다. Pro는 주간 한 칸, 5시간 한도가 제공되는 계정은 5h/주간 두 칸을 표시한다. 기본 배경은 투명하고 호버·누름 시만 옅은 둥근 배경을 보인다. 텍스트/게이지의 안티앨리어싱을 유지하도록 per-pixel alpha 도구 창을 사용한다. 시스템 작업표시줄 라이트/다크 설정을 따르고, 표시 창이 하나면 폭을 줄인다. 사용량/잔여량 옵션은 게이지와 숫자 모두에 적용한다. 조회 중/초기화 후 재확인 중의 값은 빈 게이지와 대시로 구분하며 0%로 오인시키지 않는다. 사용량이 높아지면 게이지 색도 바뀐다.

호버 애니메이션 타이머는 상태 전환이 끝나면 정지한다. 수치/테마가 바뀔 때만 다시 렌더링하고 GDI 객체와 비트맵은 즉시 해제한다. 일반 대기 중에는 데이터 확인용 500ms 타이머만 사용하며 추가 계정 요청은 없다.

개발 중 네이티브 스타일을 매 틱 다시 써서 WinForms 창 순서와 충돌하는 문제가 있었다. 창 생성 시 도구 창/비활성/최상위 속성을 정하고 이후 위치만 갱신하도록 수정했다. Visible=true만으로 통과시키지 않고 실제 좌표·최상위 속성·해당 지점의 최상단 창을 검사한다. 사용자는 이 수정 후 위젯 표시와 설정창 클릭을 확인했다. 새 게이지 디자인에 대해서는 별도 시각 확인을 요청했다.

## 검증과 한계

실제 Codex 클라이언트 2560×1528, 150% 배율에서 대상 감지·실제 계정 대시보드 표시를 확인했다. 사용자도 대시보드 설정 버튼과 위젯 표시/클릭을 확인했다.

- tests/dock.ps1 -Visual -LiveHost: 실제 대상 감지, 격리 WPF QA 창 이동·최소화·닫힘, 기존 모드 복원, 접기·펼치기/아래쪽 기준 유지/아이콘 동작. 계정 요청 없는 fixture 검사다. 실제 데스크톱을 사용하므로 별도 QA 시간에만 실행한다.
- tests/appearance_health.ps1, tests/session_metrics.ps1: 테마/조회 상태/JSONL 지표의 합성 데이터 검사다.
- tests/taskbar_lifecycle.ps1 -Visual: 실제 Explorer 경계/화살표 감지, 위젯 최상단 표면/반복 갱신·옵션 OFF·비활성·종료 정리. 저장 PNG는 위젯 렌더러 결과이며 데스크톱 스크린샷과 구분한다.
- tests/taskbar_design.ps1: 라이트/다크·기본/호버/누름·100/150/200% 배율의 실제 렌더러 결과, 투명 배경과 상태 색, Pro/표시 OFF/초기화 경계/잔여량 전달을 검사한다. 상태 비교판은 예시 수치이며 실제 작업표시줄 캡처가 아니다.
- tests/dock_occupancy.ps1: 기본 실행은 창을 만들지 않는 회피/복원 정책 검사다. -Visual을 명시한 경우에만 실제 격리 WPF 창에서 라이트/다크의 빈 여백/넓은 입력창/제거를 확인한다. 실제 Codex의 모든 페이지를 검증한 것은 아니다.
- tests/settings_cache.ps1: 설정창 재사용·탭 보존·최소화 복원·사전 준비 시 비표시·실제 창 메시지 전달을 화면 밖의 격리 WPF 창에서 검사한다. 이전 재열기 약 816ms, 캐시 적용 후 약 47~67ms를 측정했다. 사전 준비 후 첫 표시 약 233~255ms, 창 메시지→표시 약 213~217ms였으며 실제 사용자 반응도 빨라졌음을 확인했다. 모든 PC의 성능 보장은 아니다.
- 기존 WPF SelfTest·설정 선택·공유 JS 코어·RPC 테스트도 실행했다. 최근 격리 보고서는 .research 아래에 있다.

내부 UI 확장이 아닌 외부 companion이며 앱 내부 공간을 예약하지 않는다. 색상 띠 관찰은 레이아웃 추정이므로 테마·디스플레이 드라이버·특수 패널에 따라 확인이 안 될 수 있다. 이때 보수적인 여백/숨김으로 동작한다. 실제 혼합 DPI 모니터 이동, 다른 가상 데스크톱/여러 Codex 창 전환, 모든 작업표시줄 정렬·자동 숨김·전체 화면 조합은 미검증이다. 일반 화면으로 자동 복원하는 최종 수정본의 사용자 확인은 별도로 기록한다. 기존 설치본·사용자 설정은 변경하지 않았다. macOS 신규 UI는 구현/실기기 검증하지 않았다.

## 2026-10-28 입력 지연·포커스 간섭 조사

사용자는 개발용 대시보드와 위젯 실행 중 입력 이상·포커스 이탈·지연을 보고했고, 개발 프로세스가 종료된 뒤 정상으로 돌아왔다고 확인했다. 조사 당시 개발용 Monitor/Taskbar/QA 프로세스는 없었으며 기존 설치본 PID 10296만 실행 중이었다. Codex와 기존 설치본은 종료하거나 교체하지 않았다. 이 QA는 실제 Windows 데스크톱에서 수행했으며, 이 작업을 위한 샌드박스·가상 머신·에뮬레이터를 실행하지 않았다.

확인한 요인은 다음과 같다.

- `dock_occupancy.ps1`은 실제 창을 최상위로 표시하고 `Activate()`를 호출했다. `dock.ps1`의 테스트 호스트도 일반 `Show()`를 사용했다. 작업 중 이 테스트를 실행하면 사용자의 전면 창을 빼앗을 수 있다.
- `settings_cache.ps1`은 창을 화면 밖으로 옮기고 명시적인 Activate/SetForegroundWindow 호출을 제거했으나, WPF의 기본 ShowActivated 동작은 막지 않았다. 화면 밖의 창도 포커스를 가져갈 여지가 있었다.
- 개발 모니터 종료 보고서에 CPU 127.281초 / 경과 722.1초가 기록됐다. 이는 논리 프로세서 하나 기준 평균 약 17.6%이며, UI 스레드 CPU는 88.047초였다. 별도 8초 구간 측정에서는 약 29.7%가 관찰됐다. 시스템 전체 17.6%/29.7%라는 뜻은 아니며, 테스트/추적 로그가 켜진 개발 실행 수치다.
- 창 부착 모드에서 숨겨진 패널을 빠른 주기로 재확인하는 경로가 있었고, 객체 이벤트 훅도 시스템 전체에 등록되어 있었다. 이벤트를 거르는 C# 콜백 앞까지 다른 앱 이벤트가 전달되는 불필요한 부담이 있었다.
- Windows 소스 정적 검색에서는 SendInput/keybd_event/SetWindowsHookEx/AttachThreadInput/BlockInput이 발견되지 않았다. 기존 GetAsyncKeyState 호출은 마우스 왼쪽 버튼만 조회한다. 창 부착은 NOACTIVATE 도구 창, 작업표시줄은 ShowWithoutActivation/NOACTIVATE이며 명시적인 설정 열기에는 전면 활성화가 있다. 이것만으로 모든 실제 포커스 동작이 안전하다고 입증되는 것은 아니다.

개발 소스에 다음 재발 방지 처리를 추가했다.

1. 실제 창/위젯을 띄우는 dock/taskbar 수명 주기 검사는 `-Visual` 명시가 필요하다. 색상 띠 검사는 기본적으로 창 없는 정책 검사만 수행한다. `tools/verify_package.py`도 ZIP 검사와 `--visual` 실제 WPF 검사를 구분하며 생략 여부를 출력한다.
2. 화면 밖 설정창 테스트는 ShowActivated=false와 SourceInitialized의 WS_EX_NOACTIVATE를 함께 적용한다.
3. 전면 창 변경 이벤트만 전역으로 받고, 위치·표시·최소화 이벤트는 대상 Codex PID에 한정한다. 자체 프로세스 이벤트는 제외하고 대상 재선택 시 다시 연결한다. Pet 모드와 Codex 비활성 상태에서는 부착 모드 이벤트 훅을 해제한다.
4. 숨겨진 패널의 50ms 재시도는 최초 표시 안정화 구간에만 사용한다. 백그라운드 창에서는 완화된 주기를 사용한다. 사이드바 상태 파일도 크기·수정 시각이 같으면 다시 읽지 않는다.

참고로 기존 설치본의 별도 6초 관찰에서는 CPU 약 3.38%/논리 프로세서 하나, 메모리 83.3MiB였다(논리 프로세서 8개). 서로 다른 시점·작업량의 짧은 측정이므로 개발본과의 성능 비교 실험으로 해석하지 않는다. 포커스 간섭 가능성은 테스트 코드에서 확인했지만 지연과 입력 이상 각각을 어느 코드 한 곳이 전부 일으켰는지는 아직 분리 재현하지 않았다.
